## 已完成：T11 结算页「已发」与应付单对不上（2026-10-16 第五批）

**你反馈的现象**：给沈八付了一部分 500，往来页显示还剩 4000，但结算页还是显示 4500 未付。
**你要求的修法**：已付/还欠按**累计口径**、**各种付款方式总和**显示；超过未结额**硬限制**；
存量数据启动时修正；结算单只记"这一期该结多少"；发放只在总览表做；已结清默认不显示。

### 根因（我查了你的库，数据说话）

```
cost#6   沈八 人工费 4500
arap#6   应付单 4500   已冲 500   状态=部分    ← 对的
offset#1 → 冲的是 arap#6，来自一笔付款流水 500
settle#1 结算单 应付 4500   已发 0   状态=未发   ← 错的
```

**`labor_settle.paid_amount` 是结算页自己维护的一个字段，跟应付单上的冲销记录是两套数据。**
钱可以从 4 个入口进来（收/付款页、冲销弹窗、登记已付、结算发放），**前三个都不会回写结算单**。

**更严重的是**：发放时的上限是按这个错的数算的 → 结算页会允许你再发 4500，
而实际只欠 4000 —— **这是多付钱的风险，不只是显示难看**。

### 改了什么

| # | 改动 |
|---|---|
| 1 | **「已付」不再存在结算单里**，一律由该对象名下应付单上的**全部冲销记录**现场算出。钱从哪个入口付的都算得进来 |
| 2 | 结算页新增**「欠款总览」**（一对象一行、累计口径）：`应付金额（累计） / 已付（累计） / 还欠 / 状态 / 付款方式构成 / 本期该结` |
| 3 | **付款方式构成**合成一列：如「微信 300 + 现金 200」（现金/微信/银行卡/转账都体现） |
| 4 | 时间段**只决定显示哪些对象**，不改累计金额（"本期该结"列才体现时间段） |
| 5 | **发放上限改为真实未结额**（累计应付 − 已付），超过直接 400 拦住，**防多付** |
| 6 | **发放按钮只在总览表**；下面的「本期结算单」只做查看/删除 |
| 7 | **已结清的对象默认不显示**，勾选「含已结清」可看全部 |
| 8 | 新增 `GET /api/labor/overview`、`POST /api/labor/pay`（按"项目+类别+对象"发放，不依赖结算单） |
| 9 | 迁移：启动时把存量的 `paid_amount` 清零（避免以后有人误读旧数字） |

### 顺带查出并修掉的一个真 bug：**冲销不看付给谁**

修的过程中测试暴露出来的：原来自动冲销只按「同项目 + 同业务类型 + **日期最早优先**」匹配，
**完全不看这笔钱是付给谁的**。于是给李四发 1500 工资，会先冲掉**张三**更早的那笔欠款，
李四那笔还挂着 —— 从"谁欠谁"的角度**这钱记错人了**。

现在是三级优先：① **对方一致 + 业务类型一致** → ② 业务类型一致 → ③ 全部未结（兜底）。
后端 `offset_service` 与 mock 同步修改。

> 这条你没提，是我在验证时撞出来的。如果你觉得"就该按日期最早冲、不管付给谁"，告诉我改回去。

### 假数据（mock）也修了两处

1. **种子里项目1的人工费没有对应的应付单**（真实后端录成本一定会生成），补上了
2. 往来列表的**状态**原来直接沿用库里存的值，现在改成和金额一样**按冲销记录现算**
   （否则会出现"已冲销 1500 / 未结 0 / 状态却是未收付"这种自相矛盾的行）
3. mock 的"录成本→生成应付单"加了**幂等守卫**（开发模式副作用跑两次会造出重复单据）

## 已完成：L1 表头吸顶（2026-10-17）

**原来是什么问题**：长列表往下滚，顶部工具条吸住了，但**表格列名滚没了**——
看到一串数字不知道哪列是哪列，要反复往上翻。

截图（`docs/assets/`）：
- `L1-0-修复前-列名消失.png` —— 修复前：只有数据行，没有列名
- `L1-2-滚动后列名仍可见.png` —— 修复后：列名贴在工具条下方
- `L1-3-结算页多表吸顶.png` —— 一页多张表也各自吸住

**根因**：antd 用 `.ant-table-content { overflow-x: auto }` 包住表格，
这个横向滚动容器会让 `<thead>` 的 `position: sticky` **失效**（实测 `position` 仍是 `static`）。

**改法（没碰横向滚动，旧方案担心的风险不存在）**：
用 antd / rc-table 自带的 `sticky`——它把表头渲染成**独立的粘性容器**
（`.ant-table-sticky-holder`），**不依赖 `<thead>` 的 `position: sticky`**，所以不受那个滚动容器影响。

- 改在**共用组件** `DataTable` 里，**14 张表 / 9 个页面一次全覆盖**
- 成本页（`Cost.tsx`）直接用 antd `Table`（带 `Table.Summary` 合计行），单独接上同一个偏移算法
- 偏移量（让开工具条多高）**按 `.pims-toolbar` 实际高度动态算**，工具条换行也不会盖住表头

**顺带验证过的两件事**（怕改坏）：
1. **宽表横向滚动时，吸顶表头跟着表体一起滚**，逐列比对左边缘一致（`/projects` 滚 300px 后 th 与 td 完全相同）
2. 页面**没有新增横向溢出**（1280/1440/1680/1920 四档全部 `scrollWidth == clientWidth`）

**回归测试**（`tests/overflow.spec.ts`，新增 3 条）：
- 成本页滚动后列名可见且不被工具条盖住
- 8 个页面逐页确认启用了吸顶容器（证明是全站生效，不是只修了一页）
- 宽表横向滚动后表头与表体列不错位

> 顺带修正了溢出检测脚本：吸顶表头是"表头副本"，它 `overflow:hidden` 且内部表格比它宽
> （宽度跟 `scroll.x` 对齐），几何上伸出视口但被自己裁住、**页面实际没有横向滚动条**。
> 检测规则补上"用 overflow:hidden 裁掉超宽内容的容器"这一条，避免误报 63 处。

## 已完成：「完工」锁项目（2026-10-17）

**你的原话（早先）**：「这个后续的理想状态肯定是…完工后锁项目、改数据需输密码」。

### 口径（你逐条确认过）

| 项 | 定的是 |
|---|---|
| 锁什么 | **所有写操作**：成本、收付款流水、往来单、冲销/撤销、结算发放、库存出入库、**项目档案本身**、删项目 |
| 怎么放行 | 输**登录密码** → 解锁 |
| 解锁多久 | **一直有效，直到你手动点「重新锁定」**（不是倒计时） |
| 密码 | 就用**登录密码**，不再多记一个 |
| 入口 | 项目列表 + 项目详情都有「完工」按钮，带确认 |
| 撤销完工 | 支持，**要密码** |
| 重启后 | 解锁状态**保持**（存在数据库里） |

### 关键的实现选择

**① 校验放在后端，不是藏按钮**
前端藏按钮只是提示，接口仍可被直接调用。所以写操作统一走
`services/locks.py:ensure_mutable()` —— 一个只管模型、不依赖任何 service 的小模块，避免循环依赖。

**② 被拦时不让你重做一遍**
后端 409 带 `data: {reason: "project_locked", project_id}`，
前端 axios 拦截器接住 → **自动弹密码框 → 解锁 → 自动重试刚才那次操作**。
你点"保存"被拦，输完密码就保存好了，不用回去再点一次。

**③ 只读永远不受影响**
完工项目照样能看、能预览结算、能导出；`preview()` / `settlement_overview()` 这些只读函数**特意不加锁**。

**④ 加锁不要密码，解锁/撤销才要**
「完工」和「重新锁定」是往安全方向走，不要密码；「撤销完工」「解锁」要密码。

## 已完成：项目详情页整片空白（2026-10-17 你截图报的）

**现象**：进「项目详情」页，项目名称、甲方、预算、实际成本**全是 `-` 和 `0.00`**。

**根因（真实故障，不是今天改坏的）**：

| | 返回结构 |
|---|---|
| 真实后端 `GET /api/projects/{id}` | **扁平**：`{id, name, status, client_budget, ...}` |
| 前端「项目详情」页取数 | 按**嵌套**取：`overview.project` / `overview.metrics` |
| **mock**（自动化测试跑的） | 返回**嵌套** —— 跟后端不一致 |

于是：**真实页面一直取不到数（整片 `-`），但 59 条 Playwright 全绿**——
因为它们跑在 mock 上，而 mock 恰好是对的。这是个典型的"假绿"。

**修法**：后端这个接口改成**两种结构都返回**（嵌套 + 扁平），谁也不破坏：

```python
data = project_service.overview(db, project_id, start_date, end_date)  # 嵌套
data.update(project_service.serialize(project))                        # 扁平兼容
data.update(project_service.compute_metrics(...))                      # 扁平利润指标兼容
```

顺手给这个接口加了 `start_date` / `end_date` 参数（页面本来就在传，之前被忽略）。

**防止再犯**：

1. 新增**契约测试** `test_项目详情同时返回嵌套与扁平结构` —— 锁住两种结构都必须有
2. mock 也改成同时返回两种，让两边口径真正一致
3. 这个 bug 能藏这么久，是因为**自动化测试全跑 mock**；
   以后碰到"页面上没数"这类问题，应该先用真实后端验一遍（本文件「必读」里记着了）

## 已决定不做（2026-10-17 你确认）

### 结算页「直接给某人付款」（借支 / 预支 / 没工天的人）

**你的话**：「那我觉得是不是没必要，实在需要到时候就是直接开一个预支的功能了」

**结论**：**不在结算页加这个口子**。以后真有需要，**另开一个独立的「预支」功能**，而不是把它塞进结算页。

**当时的缺口是什么**（留档，免得以后重新分析）：

- 结算页的发放对象**只来自成本**（`due_map` 从成本表汇总），没录过成本的人不会出现
- 后端会挡：`「李四」没有可结算的成本`
- 钱不是完全记不了——「收/付款」页可以记「预支」类型的付款流水
- **真正的缺口在后面**：那笔预支是纯现金流出、不挂欠款；等这人后来干活生成了应付单，
  **系统不会自动扣掉之前借的钱**，得手工去旧流水上点「冲销」（能办但容易忘）
- 自动冲销也帮不上：预支是 `advance`、人工费是 `labor`，类型不匹配会一路退到兜底

**如果将来要做「预支」，建议的设计方向**（现在不做，只记着）：

1. 预支作为**独立单据**（不是普通付款流水），记录"我预先给了某人多少钱"
2. 结算发放时，把这个对象名下**未抵扣的预支**列出来，支持"先扣预支、剩下的付现金"
3. 预支要有余额概念（借 2000 抵了 1500，还剩 500 可继续抵）
